# Bundle JS-3A-003 — the corpus positions are derived now, and why that did not pin more rows

**Collected:** 2026-09-02. **Milestone:** JS-3a. **Owner:** profile architecture owner.
**Reviewer:** none.

**What this bundle is.** [Bundle JS-3A-001](../js-3a/README.md) recorded, as exclusion 4, that only
four corpus rows pin a position:

> Writing a position on every row would mean hand-computing offsets into bytes the producer
> assembles, which no reader could check; having the producer ask the verifier for them would be
> recording the answer under test.

**Both reasons are true and neither is exhaustive.** There is a third way, and it is taken here.
**It did not pin more rows, and section 3 says why that is the honest outcome rather than a
shortfall.**

---

## 1. The third way

The producer computes the position from **its own construction** — the section it put the defect
in, the offset it put it at, and the position table it wrote — and the replay compares that against
what the verifier computed from what it **read**.

Two derivations of one fact, and they can disagree. That is the shape rule K2 uses for a
composition's profile set and rule J8 uses for the report's own figures. It is neither of the
things the exclusion ruled out: nothing is hand-computed into bytes, and nothing asks the verifier.

**The hand-computed strings stay.** They were written by a human against the format document, and
the first thing the derivation had to do was reproduce them — so `Pinned` holds the two answers
against each other and **the producer refuses to write a corpus when they differ**. A derivation
that replaced the literals would be a second implementation with nothing to check it.

## 2. What it covers

| Entry | Pin | Derived |
|---|---|---|
| `an-unknown-opcode` | `2:0:0:0` | yes — the offset is *found* in the code bytes, the empty table gives the reserved zero pair |
| `a-position-row-inside-an-operand` | `2:1:1:1` | yes |
| `a-refusal-covered-by-the-second-position-row` | `2:3:7:5` | yes — the offset is `Array.IndexOf(code, 0xFF)` |
| `wrong-magic` | `-1:0:0:0` | **no, and the derivation refuses to express it** |

`wrong-magic` refuses before any frame is entered, so its position names no section. `PinnedAt`
throws rather than inventing an index for it. **Every pin that names a section is derived; the one
that names none is not.**

**The corpus is byte-identical after the change.** `corpus-regeneration.log` records it: same 66
entries, same hashes, same manifest. That is the evidence the derivation is right — it reproduced
three human answers without moving a byte.

## 3. Why no new row was pinned, which is the finding

Pinning an unpinned row means knowing **which byte** its refusal reports. For
`a-constant-index-past-the-pool` the producer knows where it put the bad index; it does *not* know
whether the verifier reports the instruction's start offset, the operand's offset, or the offset it
had reached — and **JSD-0009 does not say.** It defines what the fields *mean*:

> `ByteOffset` — Always populated. What it is an offset into is what the section index says.

It does not define, per stage or per diagnostic, which byte a refusal is *about*. So the three
available moves were: guess, ask the verifier — which is the exclusion's second horn — or **write
the convention down first**.

**The convention is not written down, and pinning rows before it is would encode whatever the
verifier happens to do today as though it had been decided.** That is the next piece of work and it
is a decision record, not a corpus edit.

## 4. Results

`pin-controls.log`: three injections, each breaking a different side, and the producer refuses
every time.

| Control | Write | What it said |
|---|---|---|
| `the-hand-computed-answer-is-changed` | refused | `derives 2:3:7:5 … hand-computed is 2:3:7:6` |
| `the-derivation-reads-the-wrong-section` | refused | `derives 1:3:7:5 … hand-computed is 2:3:7:5` |
| `the-position-table-loses-its-second-row` | refused | `derives 2:3:1:1 … hand-computed is 2:3:7:5` |

The second is the one worth having: a derivation reading the wrong section would give every future
pin a plausible wrong index, and only the hand-computed answers would notice.

Suite: 172 architecture and 207 contract tests, green. Corpus replay: 21 checks passed. Corpus
regenerated byte-identical.

## 5. Exclusions — what this bundle does not show

1. **Still four rows of sixty-six.** The mechanism to pin more exists; the convention that would
   let it be honest does not. Section 3.
2. **Two derivations agreeing is not the encoding being right.** A shared misunderstanding — both
   sides reading the covering row the same wrong way — agrees. The hand-computed literals are what
   stands against that, and they were computed by one person once.
3. **The derivation implements the covering-row rule a second time.** That is the point and it is
   also a cost: JSD-0009's rule now has two implementations, and a change to it has two places to
   reach.
4. **`wrong-magic` is unchanged and hand-computed**, per section 2.
5. **The ledger's figure for this was stale and is corrected here** — it said four rows pin and
   *fifty-five* pin none, from when the corpus held 59 entries. It holds 66. **The sweeps in
   JS-ANDROID-017 and -018 did not catch it**, because `corpus rows` is not one of the fifteen
   countable subjects their vocabulary reads, which is the reach limit both bundles stated.
6. **Nothing here moves JS-3a.** The oracle half is untouched and still needs a human.
