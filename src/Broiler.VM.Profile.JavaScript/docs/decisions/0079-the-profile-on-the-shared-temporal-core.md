# JSD-0079 - The profile on the shared Temporal core: SJL-10.4's cut-over

**Status:** Decided 2026-10-18. It applies
[JSD-0078](0078-the-temporal-core-moves-to-the-shared-algorithms-library.md), the area's verdict. **The code
landed in the changes before this record**, so that the evidence this record cites could be taken at
commits of the code it judges; this record is the change after them.

**Date:** 2026-10-18.

**Owner:** the JavaScript profile owner. **Co-signers:** the core architecture owner, for rule I1's
allow-list and rule I5's register, and the release owner, for the notices rows. **All three roles are held
by one person** (EX-30), and this record does not claim that anyone independent has read it.

**Milestone:** the shared JavaScript libraries programme's SJL-10, work package SJL-10.4
([the milestone](../../../../docs/javascript-shared-libraries/milestones/sjl-10-temporal.md)). SJL-10 started
before SJL-6 and SJL-8, which it waits on, met their gates, and it may not meet its gate before they meet

## Context

JSD-0078 accepted the Temporal core's seven sub-areas - records and limits, balancing, durations and
rounding, differences, the grammar, calendars and serialization - with the options' rules going with the
sub-area each serves, and placed them in `Broiler.ECMAScript.Algorithms`. SJL-10.3 built them there, under
`Broiler.ECMAScript.Temporal`, at Broiler.JS `e33b53e6`. It changed nothing in this profile. This record is
the change itself: every Temporal answer the family computed in its core is the shared library's, the code
that computed it is deleted, and row R6 and row D12's day window are corrected. The evidence that judges it
is bundle [`sjl-10-001`](../../../../docs/evidence/sjl-10-001/README.md), under the rule SJL-10.1 committed
before any of this code existed.

**The changes**, each building, each with the tests it touches green:

## Decision

### 1. References

**`Broiler.ECMAScript.Algorithms` and `Broiler.ECMAScript.Generation` `0.1.0-preview.6`**, the shared
stream's next preview, packed locally from Broiler.JS `bf81d1b7b468d8235b672ed7dfc0327c26a4843c` and
restored from the committed feed `eng/packages/` with lock files. `bf81d1b7` is SJL-10.3's library at
`e33b53e6` with the stream's version moved, and nothing else under `Broiler.ECMAScript/` but its changelog.
**They are not on nuget.org at this record**; each `.pin` beside its package on the feed says so, and a
release of this family waits for their publication, which `eng/verify-feed.ps1` enforces.

| Package | Use | Projects rule I1 admits it for |
|---|---|---|
| `Broiler.ECMAScript.Algorithms` | product | `Broiler.VM.Profile.JavaScript`, `.Compiler`, as before |
| `Broiler.ECMAScript.Generation` | test-only | `Broiler.VM.Architecture.Tests` alone, as before |

**Rule I1 admits one version of a package**, so the allow-list's entries, the feed, the three lock files and
rule I1's witness moved to `0.1.0-preview.6` together, and `0.1.0-preview.5` left the feed, in `66b0877`.
**The package baseline moved with it**, to bundle JS-10-010, for the reason JSD-0077 gives; `packages.md`
and `support.md` name it.

**Decision: the generator package moves with the stream.** `Broiler.ECMAScript.Generation`'s code does not
change between `0.1.0-preview.5` and `0.1.0-preview.6`. The two packages are one stream with one version
(`Broiler.ECMAScript/Directory.Build.props`), and pinning the test-only package to the older preview while
the product package moves would hold the feed to two packs of one source. So both move; the generator's
tables, regenerated by rules N30 and N32, stay byte for byte.

**The Intl data assembly references nothing new.** It hands the profile the calendar table as before, and
the shared calendars read it.

### 3. Adapters

Each calls the shared library and keeps what JSD-0078's decision 3 leaves each engine - the objects and
slots, the reads in specification order and their coercion, `relativeTo` resolution and `ToTemporal*`
classification, the errors and their messages - and computes no limit, balance, rounding, difference,
calendar date or string itself:

| Adapter | What it keeps | What it calls |
|---|---|---|
| `JsTemporal.Conversions`' `Create*` and `ValidEpochNs` | The prototype from `newTarget` | `TemporalLimits.CheckIsoDate`, `CheckIsoDateTime`, `CheckIsoYearMonth` and `CheckEpochNanoseconds` |
| `JsTemporal.Conversions`' `To*`, `InstantString`, `ZonedDateTimeString` | The property reads and their order, the classification of an argument, the zone's offset | `TemporalGrammar` through the wrapper; `IsoArithmetic.RegulateTime`; `TemporalFormat`'s writers |
| `JsTemporal.Options` | Each option's read, in the specification's order, with its coercion and its own RangeError; the unit names | `TemporalOptionRules`: the rounding modes and increments, the units and their groups, the difference settings, the round and `toString` units, the seconds-string precision |
| `JsTemporal.Calendar` | The field reads (`PrepareFields`), the time, offset and zone half of `MergeFields`, the month code's parse | `TemporalCalendars`: `Canonicalize`, `MergeFields`, `DateFromFields`, `YearMonthFromFields`, `MonthDayFromFields`, `DateAdd`, `IsoToDate`, `DateToFields` and the conversions between the types |
| `JsTemporal.Durations` | The duration's reads, `relativeTo` resolution and a wall time's instant (`InterpretDateTimeOffset`) | `TemporalLimits.CheckDuration`, `DurationMath`, `IsoArithmetic.AddInstant` |
| The realm files' methods | Their reads and the zone check a `ZonedDateTime` difference in days or larger units makes first | `TemporalDifferences`, `DurationMath`'s `Compare`, `AddDurations`, `Round`, `Total` and `RoundTimeDurationToIncrement`, `IsoArithmetic`'s addition and comparison, `TemporalFormat` |
| The formatter's calendar date (`JsLocalTime.InCalendar`) | CLDR's names and numbering of the month, the era and the cyclic year (SJL-9's) | `TemporalCalendars.IsoToDate` |

**Each status is the specification's error, with this family's message** (X3: "each engine maps a status to
its own error"), in `JsTemporal.StatusError`, `CalendarError` and the wrapper's `ParseError`:

| Status | Error and message |
|---|---|
| `TemporalStatus.OutOfRange` | `RangeError`, "Temporal: *what* is outside the representable range", *what* named by the call site as before: "the date", "the date-time", "the year-month", "the month-day", "the result", "the duration"; an addition to an instant, "the result is outside the representable range of instants" |
| `TemporalStatus.InvalidDate`, `InvalidTime` | `RangeError`, "*what* is not a valid date", "the time is not valid" |
| `TemporalStatus.InvalidDuration` | `RangeError`, "the duration is not valid: mixed signs, or too large"; in `add`, `subtract` and `compare` "the time duration is too large", in `round` "the rounded time duration is too large", as before |
| `TemporalStatus.RelativeToRequired` | `RangeError`, each method's own message, as before |
| `CalendarStatus.MissingYear`, `MissingMonth`, `MissingDay`, `IncompleteEra` | `TypeError`, the property that is required |
| Every other `CalendarStatus` | `RangeError`: an unknown calendar, era or month code, an era year that disagrees, month and monthCode that disagree, a leap month the year lacks, a month or day out of range under `reject`, no reference year; `OutOfRange` as `TemporalStatus.OutOfRange` |
| `TemporalParseError` | `RangeError`: a critical annotation conflicting or unknown, a year-month or month-day outside ISO 8601, an instant outside the limits, no zone, a sub-minute zone offset, and "cannot parse" for the rest |
| An option rule's `false` | `RangeError`, one message per rule (section 7) |

The zone statuses keep JSD-0077's table, unchanged.

### 4. Corrections

**Row R6** (JSD-0078 decision D9). `new PlainDate` and `new PlainDateTime` with a year of 2^53 + 2 or ±10^20,
and `new PlainMonthDay` with a reference year of 10^20, ended the invocation
(`ProfileFault/ProfileContractViolation`): the shared `IsoCalendarMath.EpochDays` precondition threw before
the limit test. The constructors now check the limits through `TemporalLimits`, whose checks take any year
and answer a status, before any epoch-day arithmetic, so each throws the `RangeError` CreateTemporalDate and
CreateTemporalDateTime ask for. A year past `long`'s range saturates (.NET 9 and later), and every limit
check refuses it. The slice compiler's check `temporal/t1/a-year-past-2-to-the-53-is-a-range-error` runs
the six constructions and `new PlainDate(275760, 9, 13)`, which still constructs.

**Row D12's day window** (JSD-0078 decision D11). Pacific/Apia skipped 2011-12-30, so a day nudge window
back from 2011-12-31 has no length, which the pinned text asserts cannot happen. `since` in days from
2011-12-31T16:15 there, and `Duration`'s `round` and `total` in days relative to it, ended the invocation
with a .NET `ArgumentOutOfRangeException`. The library's rounding, totals and differences answer
`OutOfRange` there, which is the `RangeError` above. The check
`temporal/t1/a-day-window-a-zone-skips-is-a-range-error` runs the three and a difference in hours, which
opens no day window and still answers `PT16H15M`. `until` from the earlier date, whose window runs forward
and does not reach the skipped day, answers `PT0S` before and after. Row D12's week window stays code no
input reaches.

*(Note, 2026-10-19, at Broiler.JS's SJL-10.5.)* **Row D12's zoned branch is reached too**, by the same
skipped day: the day span whose sign NudgeToZonedTime asserts at step 8 (s7.5.35) is zero back from
2011-12-31T16:15 there to an earlier instant of the same day, such as 2011-12-31T00:00, where the
difference has no date part, when a time unit is rounded under a date largest unit, as in `since` with
largest unit `day` and smallest unit `hour`. This family's code at `14072b0` has no test of that sign, and
answered durations from outside the text's domain there, `P1DT16H` and the like. `0.1.0-preview.6`
answers the same durations, line for line, so the cut-over moved no answer there, and "No other answer
moves" below holds. The owner's decision D12 of 2026-10-19
([JSD-0078](0078-the-temporal-core-moves-to-the-shared-algorithms-library.md), section "SJL-10.5's
cut-over, read against this record") makes the answer a `RangeError`. The library answers so after
`0.1.0-preview.6`, and this family takes it with the shared stream's next version: a policy change
pending here, durations to a `RangeError`, not a correction, since no host exception escapes there. The
paragraph above is left as written.

*(Note, 2026-10-19, later.)* The shared stream's next version, `0.1.0-preview.7`, published that day from
Broiler.JS `5ddee404`, carries decision D12, and this family moves to it
([JSC-317](../roadmap.corrections.md#jsc-317)): `since` with largest unit `day` and smallest unit `hour` from
2011-12-31T16:15 back to 2011-12-31T00:00 in Pacific/Apia, `P1DT16H` on `0.1.0-preview.6`, is a `RangeError`,
the library's `OutOfRange` mapped as section 3's table maps it, and a slice-compiler check holds it. The policy
change is made; no other answer moves, and the paragraph above is left as written.

**No other answer moves**, but in its message (section 7); section 6's checks find no other.

### 5. Charging and limits

**Nothing in the area charges, and nothing does now** (JSD-0078's X3 and decision 3). The grammar's members
take the caller's meter, and this family passes none, as it charged nothing for a Temporal string before the
cut-over; no other shared member takes one. So there is no class C2, and every fuel-parity twin keeps its
base figure (section 6).

**The limits are the shared library's**, the proposal's: the ISO date and date-time limits, the instants'
±10^8 days, and a duration's limits, each answered as a status for any input. Every precondition the
library lists lies outside them, and every adapter checks the limits first.

### 7. Messages

**Decision: a message names the status the library answers, and the cause where the call site knows it.**
JSD-0054 section 5 leaves messages to this family ("Messages name the operation and what was wrong; the draft
states only the error's type"), and JSD-0078's decision 3 keeps them each engine's. This family's core
named some refusals by the cause its own code met first, which the library does not report:
- **the option rules** answer `false`, not which of the units, their order or the increment failed. Each
  rule has one message: a difference's "largestUnit, smallestUnit and roundingIncrement are not valid
  together for this difference", and `round`'s "smallestUnit and roundingIncrement are not valid together"
  or, for `Duration`, "smallestUnit, largestUnit and roundingIncrement are not valid together";
- **a field out of range under `reject`** is `FieldOutOfRange` in every calendar, ISO 8601's included, so
  "2021-2-31 is not a date" is "the month or day is out of range in the iso8601 calendar", as the other
  calendars' messages already read;
- **a year past the limits** in a property bag is `OutOfRange` for the date it would make, so "the year is
  outside the representable range" is "the date is outside the representable range";
- **a date addition past the limits** is `OutOfRange` from `DateAdd` whichever unit carried it, so its
  message is "the result is outside the representable range" where some paths said "the date"; and a
  rounding or total relative to a date reads "the date-time" where some paths said "a date-time" or "the
  result";
- **an unknown critical annotation** is one parse error, and its message no longer names the key.

The probes show every change (section 6): 44 lines in eleven probes, each with the same error type, and
the bundle keeps them line by line. No test262 case, vector or reference dataset reads a message.

## Departures from the plan

Each is this record's, and none edits JSD-0078:

- **`JsCalendars.cs` went whole.** The milestone's list names the cores of `JsTemporal.Calendar` and
  `JsTemporal.CalendarNonIso`; the calendar systems they called lived in `JsCalendars.cs`, which JSD-0078's
  calendars sub-area moves, so it is deleted with them. The formatter, its other reader, converts through
  the shared calendars (section 3).
- **The calendars stay strings in the slots.** The adapter guide leaves the representation to each engine.
  The slots keep the canonical identifier this family reads and writes, and `CalendarIdOf` converts at each
  call; a slot holding the library's `CalendarId` would change every realm file's reads for no answer.
- **A duration holds `DurationFields`**, the library's record, where it held ten doubles; `FieldsArray`
  gives `Intl.DurationFormat` and `toLocaleString` the array they read.
- **Messages name statuses** (section 7).
- **The changes are four before this record.** The packages' admission and the baseline it forced came
  first, so that the cut-over built from the committed feed; the register came after the cut-over, so that
  rule I5's test read the tree it registers.
